# Порівняння планів

| Критерій | Без контексту | З Knowledge Base |
|---|---|---|
| Розуміння поточної архітектури | вигадав модулі `data/domain/presentation`, Hilt, Room | правильно описав ланцюг Screen → ViewModel → Repository → Retrofit → FastAPI |
| Технологія backend | Node.js + Express + PostgreSQL | наявний FastAPI + Pydantic, без БД |
| Обсяг змін | ~10 кроків, нові модулі, переписування дизайну | 5 кроків, 13 конкретних файлів |
| Нові залежності | Room, Hilt, Navigation, FCM, JWT, PostgreSQL | жодної |
| API-контракт | нові REST-ресурси `/budgets`, `/expenses` без формату помилок | один endpoint, наявний формат `{"error":…}` |
| Відповідність рішенням власника | ліміти за категоріями (у iOS їх прибрали) | лише загальний бюджет, пороги 80/100% як в iOS |
| Ризик регресії ЛР2 | високий (міграція даних, новий навігаційний каркас) | низький, явні критерії «ЛР2 працює» |
| Тести | загальні «unit + інтеграційні» | конкретні граничні випадки (80%, 100%, доходи, 422) |
| Критерії готовності | відсутні | вимірювані (команди + числові приклади) |
| Документація | «оновити дизайн» | перелік документів KB, які треба оновити |

## Висновок
Без контексту AI вгадує «типовий» стек і проєктує систему з нуля: пропонує 6 нових технологій, ігнорує наявний backend і формат помилок, повертає прибрані ліміти за категоріями. Такий план неможливо виконати невеликими кроками без регресії. З Knowledge Base план вийшов мінімальним і перевірюваним. Найбільше вплинули `architecture.md` (реальний ланцюг і файли), `api-contract.md` (формат помилок і правило сумісності), `decisions.md` (D3, D8: без БД, Hilt і зовнішніх сервісів) та `ai-instructions.md` (план → один крок → diff → тести).
