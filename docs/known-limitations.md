# Known limitations

## Дефекти / обмеження поведінки
- Історія лише локальна: не синхронізується між пристроями, немає резервної копії (`allowBackup=false`), база не шифрується.
- «Очікує» не надсилається автоматично при появі мережі — лише кнопкою «Надіслати» (WorkManager не підключено).
- Історія не має пошуку, фільтрів і пагінації (для сотень записів достатньо `LazyColumn`).
- `10.0.2.2` з емулятора на машині розробника давав тайм-аут; робочий обхід — `adb reverse` (README).
- AI: див. `ai-component.md` (малий датасет, сума без валюти = UAH).
- Валютні операції не конвертуються в гривні.
- Інтерфейс лише українською (мова відповіді backend фіксована `uk`).
- Бюджет: ліміт не зберігається між запусками (зберігаються лише операції); валютні операції не враховуються; немає системних сповіщень на 80/100% (лише картка); усі збережені операції вважаються операціями поточного місяця.

## Технічний борг
- Немає DI (Hilt) і окремих use cases: залежності дає `AuraApplication` через `viewModelFactory`.
- Схема БД версії 1 без міграцій; зміна `HistoryEntity` потребуватиме `Migration` (схема експортується в `mobile/app/schemas/`).
- Навігація — рядок-стан у `MainActivity` без Navigation Compose; при додаванні екранів варто перейти на бібліотеку.
- `Network` — глобальний object; для тестів репозиторію API підміняється через конструктор.
- Увесь UI в одному файлі `CategorizeScreen.kt` (~500 рядків).
- Немає інструментальних UI-тестів (Compose UI test).
- Модель навчається при кожному старті сервера; для більшого датасету варто зберігати артефакт.
- `network_security_config` дозволяє cleartext HTTP для всіх хостів (лише для локальної розробки).

## Ризики
- Зміна полів відповіді без оновлення `ApiModels.kt` → `BadResponse` на клієнті.
- Розходження категорій між backend і mobile (іконки/кольори в `CategorizeScreen.kt` захардкожені за кодами).
- Залежність від версій AGP 9.5 / Gradle 9.6 / Kotlin 2.2 конкретної Android Studio.
